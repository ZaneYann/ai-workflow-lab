# GitHub 趋势项目速览 CLI 工具 Spec

## 1. 背景与目标

开发一个命令行工具，用于获取并查看 GitHub 全球范围内、每日维度的趋势项目，并以 JSON 格式输出，便于人工查看、脚本处理和后续集成。

## 2. 范围

### 2.1 必须支持

- 查询全球 GitHub 趋势项目。
- 默认查询每日趋势。
- 不限制编程语言。
- 支持常用条件筛选。
- 使用 GitHub 官方 API 获取数据。
- 使用 SQLite 保存项目与趋势查询结果。
- 每次查询从数据库读取已保存数据。
- 默认以 JSON 输出，支持表格输出，并可按所选输出格式导出查询结果。
- 必须支持非交互式执行，并适合脚本、定时任务和 CI 调用。
- 在 API 限流或 API 错误时输出提示信息。
- 在非彩色终端中降级为默认终端颜色/样式。

### 2.2 暂不支持

- 数据缓存机制。
- 非 SQLite 的持久化方案。
- 小众或低频使用的命令参数。
- 复杂的交互式终端界面。
- 其他输出格式作为第一阶段的必选能力。

## 3. 用户场景

### 3.1 查看当日全球趋势

用户执行默认查询命令，获得当日全球趋势项目的 JSON 列表。

### 3.2 按常用条件筛选

用户可以通过常用参数缩小结果范围，例如：

- 编程语言
- 返回数量
- 关键词
- 排序方式

具体参数名称应遵循 CLI 通用习惯，避免引入低频、难以理解的选项。

### 3.3 供脚本处理

默认 JSON 输出可供脚本或自动化流程调用。正常 JSON 结果应可被机器解析；提示信息不得破坏标准输出的 JSON，必要时输出到标准错误流。

### 3.4 导出查询结果

用户可指定文件路径，将本次筛选、排序和数量限制后的结果按所选格式保存，同时向标准输出显示相同内容。

## 4. 建议命令接口

命令名称和具体 CLI 框架待实现阶段确定，但应提供类似以下能力：

```text
github-trend [options]
```

第一阶段建议支持以下常用参数：

| 参数 | 说明 | 默认值 |
|---|---|---|
| `--language` | 按主要编程语言筛选 | 不筛选 |
| `--keyword` | 按项目名称或简介关键词筛选 | 不筛选 |
| `--limit` | 限制返回项目数量 | 工具定义的合理默认值 |
| `--sort` | 结果排序方式，例如 Stars 或当日增长 | 工具定义的默认排序 |
| `--date` | 指定趋势日期 | 当日 |
| `--format` | 选择标准输出格式：`json` 或 `table` | `json` |
| `--output <路径>` | 将所选格式的结果额外导出到文件 | 不导出 |
| `--force` | 明确允许覆盖已有导出文件 | 不覆盖 |
| `--help` | 显示帮助信息 | 不适用 |
| `--version` | 显示版本信息 | 不适用 |
| `--token` 或环境变量 | 提供 GitHub Token | 未提供 |

除上述参数外，只有在确有必要且属于常用使用场景时才增加参数。

## 5. 数据来源与认证

- 数据来源必须是 GitHub 官方 API。
- 默认允许未配置 Token 的方式运行。
- 当 GitHub API 需要更高额度或用户主动配置时，支持 GitHub Token。
- Token 不得写入 SQLite，也不得在普通日志或错误提示中明文输出。
- Token 的具体传入优先级（命令行参数、环境变量或配置文件）在实现前需明确，并应避免命令行参数造成敏感信息泄露。

## 6. 持久化设计

### 6.1 存储介质

使用 SQLite 保存趋势查询得到的项目数据。

### 6.2 读取规则

- 每次展示结果时从 SQLite 读取。
- 第一阶段不设计独立缓存层。
- 数据库文件位置应使用当前操作系统适合的用户数据目录，具体路径在实现阶段确定。

### 6.3 数据字段

至少应保存以下信息，字段缺失时使用空字符串、空值或 `-` 等明确占位符：

- 趋势日期
- 仓库全名
- 仓库名称
- 项目简介
- 项目 URL
- 主要编程语言
- Stars 数
- Forks 数
- 当日增长信息（如果 API 提供）
- 仓库更新时间
- 数据抓取时间

项目应具备稳定的唯一标识，避免同一仓库在同一趋势日期被重复保存。

## 7. API 与数据库流程

1. 解析 CLI 参数。
2. 根据日期和筛选条件查询 GitHub 官方 API。
3. 接收并规范化 API 返回数据。
4. 缺失字段填充默认占位符。
5. 将结果写入 SQLite。
6. 从 SQLite 读取当前查询结果。
7. 应用筛选、排序和数量限制。
8. 按所选格式输出结果；指定 `--output` 时，将相同内容额外导出到文件。

实现时应明确：当数据库中已有相同趋势日期和仓库记录时，采用更新、跳过或幂等写入策略；第一阶段应保证重复执行不会产生不可控的重复数据。

## 8. 输出规范

- 标准输出默认为 JSON；使用 `--format table` 以表格列表展示，每个项目一行，包含 JSON 的全部字段：trendDate、fullName、name、description、url、language、stars、forks、dailyGrowth、updatedAt、fetchedAt。字段内容不得截断或因换行变成多个项目行；可转义单元格内换行等特殊字符。
- 指定 `--output <路径>` 时将与标准输出完全一致的内容写入文件；表格导出不含 ANSI 颜色控制码，标准输出与文件均使用无颜色表格以保证一致。
- 导出内容是本次查询经筛选、排序和数量限制后的结果；空结果输出并写入 `[]`。
- 相对导出路径以进程当前工作目录为基准；不自动创建父目录。
- 目标文件已存在时默认报错，不修改该文件；仅当显式指定 `--force` 时允许覆盖。
- 查询失败时不得创建或修改导出文件；写入失败时向标准错误输出简洁原因并以非零状态退出。
- JSON 应保持稳定的字段结构，便于脚本消费。
- 无结果时输出空数组 `[]`，不视为错误。
- 缺失字段使用空字符串、`null` 或 `-` 等明确占位符，并在帮助文档中保持一致。
- API 错误或限流提示不得污染标准输出中的正常 JSON；建议输出至标准错误流。
- 成功查询的退出码应为 `0`。
- 因 API 限流、网络错误或其他外部服务错误而无法获得结果时，应给出简洁提示；具体退出码在实现阶段统一定义。

## 9. 异常与边界行为

| 场景 | 行为 |
|---|---|
| API 返回空结果 | 输出 `[]` |
| 筛选后无结果 | 输出 `[]` |
| API 限流 | 给出提示信息，不输出误导性数据 |
| API 返回错误 | 忽略该错误并给出提示信息；不得泄露 Token |
| 网络超时或连接失败 | 给出提示信息，程序可控退出 |
| 单条记录字段缺失 | 使用约定的占位符继续处理 |
| SQLite 不存在 | 自动创建数据库及所需表结构 |
| SQLite 读写失败 | 给出提示信息并以非成功状态退出 |
| 终端不支持彩色 | 使用默认无彩色输出，不影响 JSON 内容 |
| 参数非法 | 输出参数错误和帮助提示，并以非成功状态退出 |
| 查询失败且指定导出 | 不创建或修改目标文件，报告查询错误并以非零状态退出 |
| 导出目标已存在且未指定 `--force` | 不修改目标文件，向标准错误报告错误并以非零状态退出 |
| 导出父目录不存在、无写入权限或其他写入失败 | 不自动创建父目录；向标准错误报告原因并以非零状态退出 |

“无结果直接忽略”仅适用于无结果本身；API 错误、限流、网络错误和数据库错误仍需给出提示。

## 10. 非功能要求

- 命令必须适合非交互式执行，不得依赖人工确认或交互输入。
- 应适合 Shell 脚本、定时任务和 CI 流程调用。
- 参数错误、API 错误和数据库错误应通过退出码区分成功与失败。
- 输出必须稳定、可解析。
- 数据库操作应具备幂等性。
- 错误提示应简洁、可定位问题。
- 不得在日志、标准错误或异常堆栈中泄露 GitHub Token。
- 应提供自动化测试，覆盖参数解析、数据规范化、SQLite 持久化、筛选排序、JSON 输出以及主要异常路径。

## 11. 不可妥协红线

- 导出是可选能力；未指定 `--output` 时不创建导出文件，默认输出仍为 JSON。
- 导出内容与标准输出一致，不得将提示混入 JSON。
- 查询失败不得创建或修改目标文件；未经显式覆盖选项不得覆盖已有文件。
- 非交互式执行不得要求确认；错误不得泄露 Token。

## 12. 验收标准

- 可在无 Token 情况下发起查询，并正确处理 GitHub API 的正常响应。
- 可通过 Token 提升 API 使用额度，且 Token 不被持久化或明文打印。
- 默认查询全球、不限语言、当日趋势。
- `--language`、`--keyword`、`--limit`、`--sort`、`--date` 等常用参数可用。
- 结果以稳定 JSON 输出。
- 数据可以写入并从 SQLite 读取。
- 重复查询不会产生不可控重复记录。
- 空结果输出 `[]`。
- API 限流、API 错误、网络错误和数据库错误均有明确提示。
- 缺失字段使用一致的占位符。
- 默认 JSON 格式下，`--output` 导出可解析的 JSON 数组，其内容和顺序与经过筛选、排序和数量限制后的结果一致；空结果导出 `[]`。
- `--format table` 展示全部 JSON 字段，项目一行且字段不截断；与 `--output` 同时使用时文件和标准输出内容一致，均无 ANSI 控制码。
- 相对路径以当前工作目录解析，缺失父目录不会自动创建。
- 已有文件默认保持不变并报错；显式指定 `--force` 可覆盖。
- 查询失败不创建或修改目标文件；写入失败在标准错误给出原因并返回非零退出码。
- CLI 自动化测试覆盖正常导出、空结果、表格模式、已有文件、显式覆盖、查询失败和写入失败。
- 自动化测试通过。

## 13. 待实现阶段确认的细节

以下内容不影响当前产品边界，但在开始编码前必须落定：

- 项目使用的具体语言和 CLI 框架。
- GitHub 官方 API 的具体接口及其趋势数据可用性。
- Token 的安全传入方式与优先级。
- SQLite 数据库文件的跨平台默认路径。
- 默认返回数量和默认排序规则。
- 具体 JSON 字段命名及缺失值占位符。
- API 错误时的退出码约定。

## 14. 本次变更确认

- 每个项目在表格中占一行，展示当前 JSON 的全部字段；使用已有 `--format table` 参数选择列表表格，避免新增含义重复的参数。
- 输出和导出采用相同格式和内容；默认 JSON、空结果 `[]` 及 `--force` 覆盖保护保持不变。
- 上述要求取代此前表格模式仍导出 JSON 的要求。

## 15. 本机可视化操作页面

### 目标与范围

- 增加由本机启动、在本地浏览器使用的操作页面，供单机用户操作现有 GitHub 仓库查询功能。
- 页面提供现有 CLI 的查询条件：周期、语言、关键词、数量、排序和日期；默认值及输入限制与现有 CLI 一致。展示查询结果的现有字段，并提供与 CLI 现有 JSON、表格格式对应的结果查看和导出能力。
- 不增加 CLI 尚不支持的查询或产品功能；保留既有 CLI 的接口、输出、导出覆盖保护和非交互行为。
- 复用现有查询服务和数据语义，不引入新的持久化机制。现有规约第 6 节要求 SQLite，但当前代码尚未实现；本次页面不声称已满足该要求，也不将补建 SQLite 纳入本次范围。
- Token 使用本机 `GITHUB_TOKEN` 环境变量，不在页面输入、展示、持久化或泄露到浏览器和错误信息中。

### 状态与边界

- 查询时展示加载状态；空结果、输入错误、限流、网络及服务错误分别提供可理解的提示，允许用户修改条件并重新查询。
- 服务默认仅监听本机回环地址；不要求账号或多用户部署。仓库链接可在浏览器访问，服务不得把 Token 返回客户端。
- 导出为用户在浏览器主动触发的下载，内容和字段与当前查询及所选 CLI 格式一致；不得因页面加载或查询自动写出文件。
- GitHub 官方仓库搜索接口及其现有行为不变；不得将其描述为官方 Trending 榜单或声称提供不可得的当日增长数据。

### 验收标准

- 按项目文档启动本机服务后，可在浏览器完成现有查询条件的输入和查询，结果字段与现有服务一致。
- JSON 与表格结果和导出内容符合现有格式；空结果、加载、无效输入、限流与网络错误有清晰状态，重试可用。
- 验证仅本机监听、Token 不出现在页面或响应中，且查询不自动导出；原 CLI 测试仍通过。
- 通过自动化端到端或实际浏览器测试覆盖正常查询、空结果、错误及导出，并记录测试证据。

## 16. 最低 Star 数筛选

- CLI 增加 `--min-stars <number>`，本机 Web 页面提供对应的可选数字输入；不填写时不筛选，保持原有行为。接受非负整数，包括 0；非法值按现有输入错误方式处理。
- 阈值包含边界：例如 100 表示 Stars 大于或等于 100。将条件作为 GitHub 仓库搜索的 `stars:>=n` 查询限定符，使服务端在排序和数量限制前筛选；保留既有其他条件与排序语义。
- 不新增持久化状态。筛选结果用于现有展示和导出；无结果时 CLI 输出 `[]`，Web 显示现有空结果状态。
- 验收：CLI 和 Web 均能设置和清除阈值；验证 0、100 边界、负数及非整数、未设置时的兼容行为，以及与排序、数量、其他条件及导出组合。通过 CLI 和 Web 服务端到端或浏览器测试检查请求中的限定符、结果、空结果与错误，并运行现有测试。
- 本节对第 15 节“不增加 CLI 尚不支持的查询”的限制作本次功能例外；其他既有要求保持有效。
