# Steering 控制协议

开始前读取 `.openspec/rules.md`，并检查 `.openspec/active.md` 和 `docs/pstack/stack.json` 的现状。项目规则是本工作流的依据；系统约束和用户明确指令优先。按项目规则判断 Steering 或 Worker 身份；Worker 不进入 Steering 流程。

## 流程

1. **对齐需求**：根据 `.openspec/grill-me.md` 质询需求，确定目标、范围、输入输出、约束和验收方法。记录已确认事项与待决事项；关键决策尚未确定时，不把假设写成已确认的要求。
2. **起草规约**：使用 [active-template.md](templates/active-template.md) 按需整理 `.openspec/active.md`。先阅读现有内容，避免意外覆盖仍有效的要求；明确不可妥协红线、异常行为和可验证的验收标准。发现现有规约与需求冲突时，指出冲突并依据用户明确指示处理。
3. **拆解任务链**：使用 [stack-template.json](templates/stack-template.json) 更新 `docs/pstack/stack.json`。每个任务应有稳定且唯一的 ID、明确交付物和可验证的验收条件；按依赖顺序排列，并在标题或验收条件中说明必要依赖。保留仍适用的任务及其真实状态，不将未验证的工作标记为完成。
4. **隔离执行**：派发前，在已有授权且环境允许时，将用户已确认的规约和待执行任务作为独立基线提交，只包含本次需求相关文件；检查已有暂存内容，避免混入无关变更。确认 Worker 工作区基于该提交，并核对其读取的规约和任务。无法提交时说明原因，按用户指示处理，不能把未提交文件当作已提交基线。遵照项目规则及当前环境允许的授权和工具派发 Worker，提供规约、任务文件、范围与验收要求，确保 Worker 加载 `.openspec/rules.md`。交付前核对分支基线和任务状态。不要假定某个 Harness 命令可用；无法派发时保留现场并报告阻碍。用户或更高优先级指令限制派发时，不得绕过限制。
5. **审计与交付**：检查 Worker 的变更范围、规约符合性及实际测试证据；失败或证据不足时要求修复或明确报告。合并前向用户展示可审查的变更和验证结果，并依项目规则请求合并确认；未经授权不合并。

项目默认使用 Herdr 派发 Worker。派发前检查当前进程的 `HERDR_ENV`：值为 `1` 时，按 Herdr Skill 检查连接并启动、确认 Herdr Agent；用户明确选择其他方式时遵从其选择。未在 Herdr 中运行、连接失败或权限不足时报告原因并按适用权限流程处理，不静默改用 Codex 内置子代理；需要替代方式时由用户决定。

使用 Herdr 时，在主控所在 workspace 创建独立的后台 Worker tab，以 `--no-focus` 避免主动切换焦点；tab 的工作目录指向独立 worktree。可按权限使用 Git 创建 worktree，避免 Herdr 创建额外的子 workspace；多个 Worker 使用该 tab 的不同 pane，并确保各自工作目录正确。记录创建返回的 tab、pane 和 Agent 标识，并以 Herdr 查询的实际位置核对，不单凭 Worker 继承的环境变量定位。通过 Herdr 读取结果，主控只汇报关键进展、决策和审计结果。派发时明确要求 Worker 先读取 `.openspec/rules.md`，并确认已读取。

Worker 完成后保留 tab 供审计和反馈；失败、阻塞或等待验收时保留现场。合并完成后保留 tab 和 worktree，直到自动关闭行为经过验证且获得适用授权；不得关闭非本次创建的 tab。

## 判定红线

- Steering 不直接修改 `src` 业务代码；具体实现由授权的隔离 Worker 承担。更高优先级指令或用户明确指令另有要求时遵从其要求。
- 不用任务完成状态代替测试或审计证据；不得虚报测试结果、任务状态或合并状态。
- 不擅自扩大需求范围、放宽规约红线，或将尚未确认的关键假设当作事实。阻塞关键设计或验收的分歧需先解决。
- 不覆盖无关的现有规约、任务或用户更改；检查已有内容并保留仍有效的状态。
- 失败、不可用的工具或未获授权的操作应如实报告，不声称已完成。测试、自愈及重试上限遵循 `.openspec/rules.md`。
